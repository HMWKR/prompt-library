# 프롬프트 품질 공학 연구 계획서

## Prompt Quality Engineering: A Systematic Approach to AI Collaboration

---

## 1. 연구 비전

### 1.1 핵심 목표

```
"AI 협업의 품질을 예술에서 공학으로 전환"

현재: 프롬프트 작성은 "감"과 "경험"에 의존
      → 재현 불가능, 공유 어려움, 품질 들쭉날쭉

목표: 프롬프트 작성을 "시스템"과 "데이터"로 관리
      → 재현 가능, 팀 공유, 품질 측정 가능, 딥러닝 적용
```

### 1.2 연구 범위

| 단계 | 목표 | 산출물 |
|:----:|------|--------|
| Phase 1 | 품질 프레임워크 정립 | 검증된 5계층 품질 모델 |
| Phase 2 | 실증적 검증 | 논문 (CHI/ICSE급) |
| Phase 3 | 대규모 데이터 수집 | 50,000+ 프롬프트 데이터셋 |
| Phase 4 | 딥러닝 모델 개발 | PromptScorer, PromptImprover |
| Phase 5 | 오픈소스 공개 | 도구, 데이터, 모델 |

## 3. 품질 기준의 비판적 검토

### 3.1 현재 5계층 48점 시스템

| 계층 | 점수 | 비중 | 내용 |
|:----:|:----:|:----:|------|
| L1 | 18점 | 37.5% | 구조적 완성도 |
| L2 | 8점 | 16.7% | 엔지니어링 기법 |
| L3 | 6점 | 12.5% | 맥락 최적화 |
| L4 | 4점 | 8.3% | 효과 검증 |
| L5 | 12점 | 25.0% | 할루시네이션 검증 (게이트키퍼) |

### 3.2 식별된 문제점

#### 문제 1: 순환 논증의 위험
```
"좋은 프롬프트"를 정의하기 위해 만든 기준으로 "좋은 프롬프트"를 평가
→ 이 기준이 실제로 좋은 결과를 예측하는지 검증되지 않음
```

#### 문제 2: 가중치의 근거 부재
- 왜 L1이 18점이고 L4가 4점인가?
- 실증적 근거 없이 직관적으로 결정됨
- 학술적으로 정당화 어려움

#### 문제 3: 예측 타당도 미검증
```
핵심 질문: "높은 점수를 받은 프롬프트가 실제로 더 좋은 AI 응답을 이끌어내는가?"

이것이 검증되지 않으면:
- 논문 리뷰에서 거부될 가능성 높음
- 딥러닝 모델이 잘못된 것을 학습할 위험
```

#### 문제 4: 도메인 독립성 미검증
- 코딩 프롬프트와 창작 프롬프트에 같은 기준 적용 가능한가?
- "구조적 완성도"가 모든 도메인에서 중요한가?

### 3.3 Claude의 관점에서 본 품질

```
내(Claude)가 생각하는 효과적인 프롬프트의 핵심:

1. 실제 정보 접근 (Grounding)         ★★★★★
   → "파일 읽고 분석해줘" vs "분석해줘"
   → 환각 방지의 핵심

2. 검증 가능성 (Verifiability)        ★★★★☆
   → "수정 후 테스트 돌려줘" vs "수정해줘"
   → 자가 검증 루프

3. 범위 한정 (Scope)                  ★★★★☆
   → 하나의 작업에 집중

4. 구조적 명확성 (Structure)          ★★★☆☆
   → 중요하지만 과대평가됨

5. 형식적 완성도 (Format)             ★★☆☆☆
   → 있으면 좋지만 필수는 아님
```

## 4. 개선된 품질 모델 제안 (v3.0)

### 4.1 새로운 구조

```
┌─────────────────────────────────────────────────────────────────┐
│              개선된 프롬프트 품질 모델 v3.0                      │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Tier 1: 필수 조건 (Gate) - 이것이 없으면 F                     │
│  ──────────────────────────────────────────                     │
│                                                                 │
│  G1. 실제 정보 접근 (Grounding)                                 │
│      • 파일/코드/데이터를 먼저 읽게 하는가?                     │
│      • 추정이 아닌 실제 정보 기반인가?                          │
│                                                                 │
│  G2. 검증 메커니즘 (Verification)                               │
│      • 결과를 확인할 방법이 있는가?                             │
│      • 완료 조건이 객관적인가?                                  │
│                                                                 │
│  ───────────────────────────────────────────────────────────    │
│                                                                 │
│  Tier 2: 품질 요소 (Quality Factors) - 점수 합산               │
│  ──────────────────────────────────────────                     │
│                                                                 │
│  Q1. 범위 명확성 (Scope Clarity)           25%                  │
│  Q2. 맥락 제공 (Context Provision)         25%                  │
│  Q3. 구조적 명확성 (Structural Clarity)    20%                  │
│  Q4. 기술적 적절성 (Technical Approp.)     20%                  │
│  Q5. 형식적 완성도 (Formal Completeness)   10%                  │
│                                                                 │
│  ───────────────────────────────────────────────────────────    │
│                                                                 │
│  Tier 3: 결과 검증 (Outcome Validation) - 실제 측정            │
│  ──────────────────────────────────────────                     │
│                                                                 │
│  O1. 결과 정확성: AI 응답이 사실적으로 정확한가?                │
│  O2. 작업 완료: 요청한 작업이 완료되었는가?                     │
│  O3. 반복 횟수: 몇 번의 시도가 필요했는가?                      │
│  O4. 사용자 만족: 결과에 만족하는가?                            │
│                                                                 │
│  → Tier 3이 진짜 "품질"의 척도                                  │
│  → Tier 1, 2는 이것을 예측하기 위한 프록시                      │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 5. 검증 실험 설계

### 5.1 실험 A: 예측 타당도 검증 (최우선)

**목적**: 프롬프트 품질 점수가 결과 품질을 예측하는지 확인

**설계**:
```
1. 100개 프롬프트 수집 (다양한 도메인, 점수 분포)
2. 각 프롬프트를 5계층 기준으로 점수화
3. 각 프롬프트로 AI에게 작업 수행
4. 결과물 품질을 전문가 3인이 독립 평가 (1-5점)
5. 프롬프트 점수 vs 결과물 점수 상관분석
```

**성공 기준**:
- r ≥ 0.5: 기준 유효
- r < 0.3: 기준 재검토 필요

### 5.2 실험 B: Grounding 효과 검증

**목적**: 실제 정보에 접근하게 하는 프롬프트가 더 정확한 응답을 이끌어내는지 확인

**설계**:
```
조건 A (Grounded):
"src/api/auth.ts 파일을 읽고 login 함수 분석해줘"

조건 B (Ungrounded):
"이 프로젝트의 login 함수를 분석해줘"

측정:
• 응답의 사실 정확성 (파일/함수명/라인 번호)
• 환각 발생 빈도
• 유용성 평가 (1-5)
```

### 5.3 실험 C: 평가자 간 신뢰도 검증

**목적**: 여러 평가자가 일관되게 점수를 매기는지 확인

**설계**:
```
1. 50개 프롬프트 샘플 준비
2. 5명의 평가자가 독립적으로 점수 부여
3. Cohen's Kappa 또는 ICC 계산
```

**성공 기준**:
- κ ≥ 0.6: 상당한 일치
- κ < 0.4: rubric 개선 필요

## 9. 핵심 원칙

### 9.1 연구 원칙

```
1. 검증 우선 (Validation First)
   └── 모든 가정은 데이터로 검증

2. 결과 중심 (Outcome-Oriented)
   └── 입력 품질이 아닌 결과 품질이 진짜 척도

3. 재현 가능성 (Reproducibility)
   └── 데이터, 코드, 방법론 모두 공개

4. 점진적 발전 (Incremental Progress)
   └── 작은 검증 → 큰 검증 → 대규모 적용
```

### 9.2 기술 원칙

```
1. Read Before Write
   └── 실제 정보에 접근하게 하는 프롬프트

2. Verify Before Commit
   └── 검증 메커니즘이 있는 프롬프트

3. Scope First
   └── 범위를 명확히 한정하는 프롬프트

4. Context Matters
   └── 충분한 맥락을 제공하는 프롬프트
```
